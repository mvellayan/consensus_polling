## The problem (reframed)

The Supreme Court responses are "nuanced and hard to understand." Root cause is
**not** presentation — it's that the app **generates rich nuance and throws most
of it away**, and ships nine 300-600 word legal opinions with no synthesis.

Two facts that drive this plan:
1. Every justice answer already has a 3-part structure (`initialize_judges.py:102-104`):
   `Outcome` / `Certainty + Scope` / 2-4 paragraphs. The UI only uses Outcome (the
   color). `Certainty` and `Scope` are generated and discarded (`app.py:66-93`).
2. There is no cross-justice synthesis. A real SCOTUS ruling ships a **syllabus**:
   one readable paragraph saying who won, why, and what the dissent disagrees on.
   This app makes the user be their own law clerk across 9 walls of legalese.

## Architecture

```
Multi-judge job (process_judges_async, app.py:380)
  9 justices answer in parallel  →  each: Outcome + Certainty/Scope + 2-4¶
                                     │
            ┌────────────────────────┤
            ▼                        ▼
   parse Certainty/Scope     DETERMINISTIC tally (calculate_summary — exists)
   per justice (new, in code)   → "6 Support, 2 Overturn, 1 Remand" = FACTS
            │                        │
            └──────────┬─────────────┘
                       ▼
        SYNTHESIS LLM call (new, STREAMING, runs ONCE after all 9 complete)
          input:  the 9 full answers + the computed tally + parsed axes
          rule:   EXPLAIN the reasoning; NEVER recount — the number and
                  who-voted-what are fixed inputs, not LLM outputs
          output: { verdict_headline, majority_reasoning, dissent_disagreement }
          stream: accumulate tokens server-side, flush partial text into
                  job_progress.syllabus every ~1s; mark syllabus.done=true
                  ONLY when the stream completes cleanly
                       │
                       ▼
        UI: syllabus headline ABOVE the vote bar (poll renders the growing
            partial text as a "typing" reveal; latency is hidden)
            vote bar + expandable justice cards (now with Certainty/Scope
            labels) unchanged below
            ── if synthesis call fails → render bar + cards WITHOUT syllabus

Single-judge job (app.py:266-304)
  1 justice answers → SYNTHESIS call (N=1 prompt): translate the 600-word
  opinion into 2-3 plain sentences → shown above the full card.
  Same code path, branches on count: N=1 → translate, N≥2 → consensus syllabus.
```

## Failure modes (design for these)

| Codepath | Failure | Handled how | User sees |
|----------|---------|-------------|-----------|
| Synthesis LLM call | timeout / API error | **Additive degradation** — render bar + cards, omit syllabus | full results, no headline (not a blank screen) |
| Synthesis LLM | tries to miscount / misattribute | **Can't** — count + attribution are code-computed fixed inputs | always-correct tally |
| Certainty/Scope parse | model didn't emit line 2 in exact format | parser returns `None` for the missing axis, hides the label (mirror `analyze_support_level` → 'unknown') | card without that label, no error |
| Synthesis latency | +1 LLM call (~5-15s) after the 9 | **stream**: flush partial text to `job_progress` every ~1s, poll renders it growing | "typing" syllabus, no dead wait |
| Stream drops mid-syllabus | network/API cut after partial flush | `syllabus.done` stays false → **discard the partial**, fall back to bar + cards (never show a truncated verdict) | bar + cards, no half-written ruling |
| Task restart mid-job | synthesis lost with the daemon thread | pre-existing (accepted in deploy plan); job shows stale | infinite spinner — known limitation |

**No silent failures:** the only new failure (synthesis call dies) is visible by
absence of the headline, and the user still gets the complete existing output.

## What already exists (reuse, don't rebuild)

- `calculate_summary` (`app.py:369-377`) / `_calculate_summary` (`dynamodb_util.py:60-68`) — the deterministic tally. **This is the fact source for grounding.** Reuse, don't recompute.
- `analyze_support_level` (`app.py:66-93`) — outcome parser. Extend the same defensive pattern to a new `parse_certainty_scope`.
- `query_judge` (`app.py:96`) — the OpenAI Responses API wrapper. The synthesis call is the same shape, different prompt, no file_search needed.
- `scotus_job_progress` table — already carries `responses` + `summary`; add a `syllabus` field to the same progress object.
- Vote bar + cards (`script.js:401-466`, `style.css:26-28`) — unchanged; the syllabus renders above them.

## NOT in scope (considered, deferred)

- **Confidence-weighted verdict** (Definitive vote counts more than Conditional) — the real Court doesn't weight votes; would misrepresent. Skipped.
- **Self-check verification pass** on the syllabus — option A already prevents LLM-generated counts, so a second verifier LLM call is overkill at hobby scale. → TODO if trust issues appear.
- **Streaming the syllabus token-by-token** — nice polish, not core; the "summarizing…" state is enough for v1.
- **Caching syllabi for identical questions** — traffic too low to matter now.
